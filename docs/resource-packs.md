# Resource-pack capture

## Current behavior

The selected in-tree gophertunnel dialer normally downloads every upstream resource pack accepted by `DownloadResourcePack` over its RakNet chunk path. BedrockDebugProxy adds a narrow per-connection adapter for the HTTP URL form of `ResourcePacksInfo`: when an upstream offer contains a URL, the adapter downloads and validates that archive before gophertunnel handles the offer, then exposes it through gophertunnel's public `ResourcePackCache` hook. This allows URL-delivered packs to complete negotiation while retaining the URL on the reconstructed pack for capture.

Before the listener offers a prefetched URL pack to the real Bedrock client, the proxy creates an equivalent archive-backed pack with an empty `DownloadURL`. The URL form is not forwarded to the client because the client must receive the bytes through the proxy's RakNet connection. This keeps the CDN request and its exact URL observable upstream while making downstream delivery use the same chunk path as a normal local listener.

Only URLs advertised by the current upstream `ResourcePacksInfo` are fetched. The URL adapter requires the complete packet body to decode successfully with no unread trailing bytes before it starts any URL download. Malformed or trailing data therefore remains in the canonical raw packet evidence without triggering auxiliary fetches. The URL must have an `http` or `https` scheme and a host, the compressed archive must match the advertised UUID, version, and size, and the advertised size must be no larger than the local 512 MiB safety bound. The URL reader also bounds the response body to the advertised size before parsing, including when the server omits or misstates `Content-Length`, so an oversized stream cannot expand the temporary archive beyond the accepted packet size. The request uses the active session context. In proxy mode this context is linked to the downstream connection, and the listener connection supplies it during login before `Listener.Accept` returns. In packs-only mode it is linked to the run context because there is no downstream connection. A canceled session stops an in-flight URL fetch. A failed URL download remains visible through the upstream cache warning and the original raw packet; gophertunnel then follows its normal chunk fallback. When that fallback stores a matching pack, it clears the earlier URL failure for the same cache key so a later lookup observes the successful archive. The adapter does not retrieve packs offline or from a separate user-supplied source.

The downstream listener mirrors the decoded upstream `ResourcePacksInfo` metadata when the upstream connection supplied it, including the required, addon, script, vibrant-visuals, and world-template fields. When the archive-backed preparation produces an equivalent payload and the protocol matches, it reuses the retained raw offer bytes. Its `TexturePacks` entries are otherwise rebuilt from the packs that the listener can actually serve, so upstream URLs are not forwarded as downstream download endpoints. When no upstream offer is available, the listener falls back to its configured `TexturePacksRequired` and `ForceDisableVibrantVisuals` policy. This keeps metadata parity separate from the transport-specific archive delivery policy.

The later `ResourcePackStack` is a separate parity boundary. Dialled connections retain the complete upstream stack, and the proxy listener reuses it when available, preserving pack order, base game version, experiments, and stack flags. Before raw reuse, the listener compares the fields known by the current protocol revision with the prepared stack. A changed prepared stack uses typed serialization, while trailing fields not understood by this revision remain in the retained raw bytes. The normal gophertunnel-generated stack remains the fallback for standalone listener callers. The evidence and implementation boundary are recorded in [`docs/research/resource-pack-stack-parity.md`](research/resource-pack-stack-parity.md).

The auxiliary offer decoder accepts an empty final DownloadURL for normal chunk-delivered packs. It uses the canonical packet decoder's byte-buffer read behavior and still rejects trailing data. The merge then selects a cached or downloaded archive once for each offered entry in offer order. It does not filter genuine repeated wire offers or rewrite archives. See [empty final URL handling](research/resource-pack-empty-final-url.md).

## Packs-only capture

Use `run --packs-only` to capture the upstream login and resource-pack exchange without starting a local Bedrock listener or requiring a second Minecraft client.

```powershell
.\bin\bedrock-debug-proxy.exe run --upstream "<UPSTREAM>" --packs-only
```

The mode uses the configured upstream authentication and the same gophertunnel dial path as a normal proxy session. It accepts only packs offered on that live upstream connection, records the packet stream and downloaded archives in the canonical capture, and closes after the resource-pack exchange. Its opt-in dial completion boundary is signalled after the received `ResourcePackStack` has been accepted and the final `PackResponseCompleted` has been flushed. It does not wait for or request world spawn, and does not capture gameplay or world state. `--web-viewer`, `--capture`, `--capture-root`, `--sync-each-event`, and the opt-in `--decrypt-resource-packs` flag remain available. `--listen`, `--follow-transfers`, and `--allow-unauthenticated-client` cannot be combined with this mode because they describe the local listener path.

This is not an offline or silent download. The upstream server receives a real Bedrock login and can log, count, reject, or otherwise handle that connection. Experience selectors still require Microsoft authentication. With no local client to supply its login metadata, the dialer uses gophertunnel's defaults. A server may therefore offer different packs than it would to a particular PC or mobile client. The capture manifest records `client_metadata_source: gophertunnel_default`. The fifteen-minute login and pack-exchange deadline remains in force. A server that defers packs until later gameplay cannot be fully captured by this mode. Captures contain sensitive identity metadata, packet data, pack archives, and server-supplied content keys. Decryption remains disabled unless explicitly requested.

Each `resource_pack.archive` event records the following evidence.

- Parsed UUID, version, name, description, and manifest plus any retained download URL and content key
- Parsed manifest and broad module flags
- Download mechanism inferred from the reconstructed pack object
- Archive byte length and SHA-256 checksum
- Upstream connection, endpoints, hop, direction, and sequence
- A blob reference to the exact archive bytes before decryption or extraction

The recorder streams the archive to disk and hashes it in one pass. This avoids allocating a second full copy of a large pack. The resulting digest is checked against the checksum computed by gophertunnel from the downloaded archive.

Archives are saved during the session, not by a later `export` command. Each archive event's `blob.path` locates ZIP bytes under `blobs/sha256/`, with a content-addressed `.bin` filename. A background reader also creates named ZIP copies and an index under `artifacts/packs/`. It does not unpack archive entries. `export` only packages the canonical capture into a portable `.bdpcap` container. See [session artifacts](session-artifacts.md).

## Ordering evidence

The current gophertunnel listener handles requested resource packs sequentially. It sends one `ResourcePackDataInfo`, services the chunk requests for that pack, and then advances to the next pack. BedrockDebugProxy uses that public listener path when offering the downloaded upstream packs to the client. It does not add a second transfer scheduler or assume a fixed ordering between independent server implementations.

The upstream dial path uses one bounded chunk-request window per connection, shared across all offered resource packs. It keeps up to 100 `ResourcePackChunkRequest` packets in flight in total, replenishes a slot as each validated response arrives, and retains out-of-order responses until the next contiguous chunk can be written to its archive. The advertised chunk size remains authoritative. Requested indices, chunk bounds, and exact fragment lengths are checked before a response enters the reorder buffer, and response bytes are copied because the packet decoder may reuse its input storage. Only the upstream download path is pipelined. The downstream listener remains sequential and keeps its existing pacing so the proxy does not add an unreviewed send-side congestion change.

The upstream connection is established before the downstream listener receives the pack list. This upstream-first buffering is intentional because the proxy must retain the exact archives and server-supplied content keys before it can offer an archive-backed copy to the real client. URL-advertised packs are prefetched with a bounded worker pool while this upstream exchange is pending, then merged with any RakNet-delivered packs in the original offer order. The console labels this wait as buffered by design and reports its elapsed duration. Live packet summaries use three-second buckets and remain enabled for the pre-spawn exchange of each transfer hop, while every packet and resource-pack archive remains in the canonical capture.

Each upstream hop has a fifteen-minute dial deadline covering authenticated login and resource-pack exchange. Featured experiences may advertise many packs and pace chunk responses across them, so a shorter deadline can abort an active exchange. The deadline still bounds a missing or unreachable transfer backend instead of leaving the downstream client in an indefinite loading state. A deadline is recorded as `upstream.dial_error` with `timeout: true`, and the listener disconnect reason identifies the elapsed limit. The deadline does not change chunk ordering or resource-pack contents.

## Opt-in decryption

The server-supplied content key is preserved because it is required to analyze encrypted pack entries. The archive itself is never overwritten. Decryption is disabled by default and can be requested with `--decrypt-resource-packs`.

Select that flag on the initial `run` command. Supported plaintext archives are derived and stored during the same session, with independent ZIP copies under `artifacts/packs/decrypted/`. They are not unpacked into individual pack files. The flag does not change skin, chunk, entity, or inventory capture. It only enables the resource-pack derivation described below.

For the documented 32-byte-key AES-256-CFB8 format, an enabled run writes the following derived events with the original `resource_pack.archive` sequence as their parent.

- `resource_pack.contents_manifest` retains each decrypted root or subpack `contents.json` as a sensitive JSON blob. Its event metadata contains counts, paths, and identifiers but not per-file keys.
- `resource_pack.decrypted_archive` retains a deterministic ZIP containing copied plaintext files and decrypted declared files. The selected root manifest.json, pack_icon.png, and bug_pack_icon.png remain byte-identical to the original archive even when contents.json declares keys for those metadata paths. Other paths retain keyed decryption. It omits the encrypted `contents.json` files because their plaintext is already preserved separately. See the [metadata research note](research/plaintext-resource-pack-metadata.md).
- `resource_pack.decrypt_error` records an unsupported format or failed derivation as a warning. It also adds a capture limitation and does not abort the connection or discard the raw archive.

AES-CFB8 is not authenticated. A derived archive is useful for analysis but is not integrity proof and never replaces the original captured bytes. The supported header, key, subpack, path, size, provenance, and verification boundaries are documented in [`docs/research/resource-pack-encryption.md`](research/resource-pack-encryption.md).

Resource-pack content keys and archives may be private, licensed, or account-scoped. They remain inside the sensitive local capture and must not be committed or published without permission.

The master key comes from the upstream server's `ResourcePacksInfo` for the current connection. BedrockDebugProxy does not derive, search for, guess, brute-force, or recover it. The current CLI has no offline decrypt command. Decryption produces a mode-restricted ZIP in the operating system's temporary directory and persistent plaintext blobs inside the capture, so it must not be described as memory-only. The temporary file is removed on normal success or failure, but an abnormal process or machine termination may leave it behind for local cleanup.

The GPL license for BedrockDebugProxy source does not relicense captured packs or their textures, models, sounds, scripts, or other assets. Rights and redistribution permission remain with the applicable creator, server operator, Microsoft, Mojang, Marketplace partner, or other rights holder. The precise data flow and legal-risk distinctions are documented in [`docs/legal-and-responsible-use.md`](legal-and-responsible-use.md).

## Evidence and validation

The implementation follows the `ResourcePacksInfo`, pack download, `ResourcePackCache`, `FetchResourcePacks`, `Pack.ReadAt`, `Pack.Checksum`, and sequential listener delivery behavior reviewed in Sandertv gophertunnel `v1.61.0` at commit `283a5a97dfe65da94bcc0b401807f6aefa9e72ee`. Its default dial path requests `ResourcePackChunkData` over RakNet even when `ResourcePacksInfo` advertises an HTTP URL. The upstream chunk pipeline is a narrow project-side compatibility improvement based on the vanilla request-window behavior described in [gophertunnel PR #509](https://github.com/Sandertv/gophertunnel/pull/509). The PR remains an upstream research reference, not a dependency update. BedrockDebugProxy's adapter prefetches that URL through the bounded, context-aware `resource.ReadURLLimitedContext` helper and supplies a cache hit before the default path is selected. The URL therefore remains observable both in the raw packet event and on the reconstructed `resource.Pack`; the exact archive bytes remain the canonical evidence. The downstream listener receives an archive-backed copy with no URL and serves it through RakNet chunks.

At the same pinned revision, `minecraft/listener.go` copies the listener's offer policy into the downstream connection before `FetchResourcePacks` dynamically returns the upstream archives. BedrockDebugProxy now retains both the upstream `ResourcePacksInfo` metadata and its raw bytes on dialled `GameData`. A narrow listener callback selects the raw bytes only after the prepared typed payload matches, while URL entries remain intentionally removed from any rebuilt downstream copy.

A verified The Hive session showed that the upstream initial offer used `TexturePackRequired = true` while its later stack used `TexturePackRequired = false`, and the session still reached spawn. The packet sequences, raw blob hashes, source definitions, interpretation, and limits are recorded in [`docs/research/resource-pack-negotiation.md`](research/resource-pack-negotiation.md).

Synthetic archive tests verify byte equality, content-key retention, metadata, endpoint context, stream sizing, deduplication, encryption vectors, root and subpack decryption, failure retention, derived event ancestry, and final capture integrity. URL-cache unit tests additionally verify URL prefetch, response-body bounds, content-key retention, duplicate-offer suppression, malformed packet handling, advertised metadata mismatch, and URL removal from the downstream copy. Nested gophertunnel tests verify raw offer retention and exact reuse only for equivalent payloads, and the proxy loopback integration test verifies the retained downstream offer bytes. For a routine pull request, use the stamped packs-only smoke workflow when the changed behavior is observable during upstream login and resource-pack exchange. Use focused tests or fixtures for behaviors outside that boundary. Real-client validation across servers offering no pack, one pack, multiple packs, an advertised HTTP URL, RakNet delivery, and encrypted entries is part of release validation. For an advertised HTTP URL, verify that the raw upstream `ResourcePacksInfo` retains the URL, the capture records the reconstructed archive with `delivery: "http"`, and the downstream `ResourcePacksInfo` has an empty URL and uses the typed fallback. The release client session verifies completion using downstream `ResourcePackDataInfo` and `ResourcePackChunkData`.
