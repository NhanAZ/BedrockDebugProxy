# ADR 0005 - Re-check deferred login packets after state transitions

## Status

Accepted on 2026-09-14.

## Context

Gophertunnel defers packets that arrive before the current login state expects their IDs. The queue preserves
the packet for a later read, but a state transition did not previously re-check that queue. A featured
experience can therefore send a valid packet early, advance the connection with a later packet, and then wait
forever because no new packet arrives to trigger another read.

This occurred in the Enchanted hop 2 capture `session-20260914T105050Z`, generated by BedrockDebugProxy revision
`96d8a01201d48b4a069c0e649374452a12b9f207`. The upstream server sent `ResourcePacksInfo` (packet ID 6) before
`PlayStatus` (packet ID 2). Gophertunnel deferred the resource-pack offer, handled `PlayStatus`, and then never
sent the corresponding `ResourcePackClientResponse`. The upstream dial timed out after five minutes while the
downstream client remained on the resource-pack loading screen. The capture retained 999 events, 530 blobs, and
zero capture write or decode errors, so the failure was in login-state progression rather than archive integrity.

## Decision

The in-tree gophertunnel compatibility patch re-checks deferred packets whenever `Conn.expect` advances the
login state. It drains only the first deferred packet while that packet's ID is currently accepted, preserving
the arrival order and leaving later packets queued until their state is reached. A deferred decode or handling
error closes the connection with the underlying error instead of leaving the dialer blocked.

The bridge remains read-only for gameplay packets. Resource-pack archives, raw packet payloads, packet order,
and decode failures remain observable in the canonical capture. Each upstream transfer hop still creates a new
gophertunnel connection and therefore obtains and delivers that hop's own resource-pack set.

## Consequences

Servers may send valid login and resource-pack packets in different orders without creating a state-machine
deadlock. In particular, a `ResourcePacksInfo` packet received before `PlayStatus` is processed as soon as the
login state reaches the resource-pack phase. A packet that is genuinely invalid for the current sequence remains
deferred and is not silently discarded or reordered.

This is an in-tree compatibility patch, not a claim that every featured-experience sequence is supported. The
revision-matched Enchanted live test for commit `a600bbff88334fc121a7163a35e8f1f5b8da02b6` completed successfully.
The capture showed a distinct pack set on the transfer target, so the two hops were not treated as one shared
resource-pack exchange.
